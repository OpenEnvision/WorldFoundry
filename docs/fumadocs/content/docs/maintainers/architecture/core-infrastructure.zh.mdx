## 本层为何存在

`worldfoundry/core` 是每个 model family 都复用、但都不拥有的共享推理基础设施。checkpoint 加载、state-dict remap、attention 后端、分布式 collectives、VRAM 放置与 offload、kernel、配置、媒体 IO、memory 契约、安全 guardrails 都只在此实现一次。family 包（`worldfoundry/base_models/*`、`worldfoundry/synthesis/*`、`worldfoundry/pipelines/*`）组合这些原语，但不得重新实现它们。

当你打算把某个工具复制进某个模型目录时，本层就是你要先读的。规则很明确：如果一个能力可服务多个 family，就先放进 `core`。扩散如何消费本层见 [原生扩散](/zh/docs/maintainers/architecture/native-diffusion)，pipeline/operator 如何消费见 [模型运行时](/zh/docs/maintainers/architecture/model-runtime)。

## 依赖规则

`core` 可依赖 PyTorch、`diffusers` 的 model/operator 原语与窄范围第三方库。它不得 import `worldfoundry.pipelines`、`worldfoundry.synthesis`、`worldfoundry.operators`、`worldfoundry.base_models` 的 family 包，或 `worldfoundry.evaluation`。依赖边是从 family 包指向 `core`，绝不反向。

这让 family 包保持精简：一个模型目录只含 checkpoint 兼容的张量算子与契约适配器，而不是第二份 offload manager、分布式 bootstrap、kernel registry 或量化系统。当你发现自己要在 family 包里加这些东西时，先把它移到 `core` 再 import。

<Callout type="info">
  扩散包在其自身边界上重申此规则，见 [原生扩散](/zh/docs/maintainers/architecture/native-diffusion)。通用 attention、transformer、加载、offload 原语在 `core`；扩散域契约、scheduler、recipe 在 `base_models/diffusion_model`。
</Callout>

## 被谁消费

- **扩散** —— `base_models/diffusion_model` 经 `core/model_loading` 加载 checkpoint，经 `core/attention` 跑 attention，经 `core/vram` 做 offload。其 `optimizations/` 只是 core policy 的再导出，不是并行实现。
- **Hosted 与 native runtime** —— `synthesis/` 经 `core/io` staging 输入，经同一套媒体助手写 artifact。
- **Memory** —— `core/memory/base.py` 定义契约；`synthesis/*/memory` 的流式/长上下文状态与 `synthesis/action_generation/memory.py` 的动作策略 trace 状态实现它。
- **分布式执行** —— `core/distributed` 是模型并行组初始化的唯一位置；任何 family 包都不得自启 NCCL group。

## 不属于此处的内容

训练入口、数据集、dataloader、loss、callback、仅增强模块、实验脚本都不属于 `core`，也不属于 `base_models`。`core` 是推理基础设施；若某模块只在训练时有用，不要加到这里。

全包目录级地图见 [代码地图](/zh/docs/maintainers/architecture/file-index)。模型调用如何流经这些原语见 [模型运行时](/zh/docs/maintainers/architecture/model-runtime) 与 [Runtime 组装](/zh/docs/maintainers/architecture/runtime-assembly)。
