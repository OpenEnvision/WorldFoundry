## Repository workflow

The root [CONTRIBUTING.md](https://github.com/OpenEnvision/WorldFoundry/blob/main/CONTRIBUTING.md)
owns contribution conventions. Use a focused branch and the environment required
by the affected runtime. New Python functions and public contracts are annotated;
use Ruff and ty for Python checks and run pre-commit on staged files. Preserve
lazy control-plane imports and upstream attribution.

Each contribution commit carries a
[Developer Certificate of Origin](https://developercertificate.org/) sign-off
using the contributor's configured name and email:

```bash
git commit --signoff -m "Describe the scoped change"
```

Use the repository's [PR template](https://github.com/OpenEnvision/WorldFoundry/blob/main/.github/PULL_REQUEST_TEMPLATE.md).
Include exact commands, results, resource requirements and relevant artifacts.
An applicable check that failed or did not run remains visible in the evidence;
imports and mocked contracts are not checkpoint-backed inference results.

Obtain the applicable maintainer/code-owner review and passing checks before
merging. Follow [CODEOWNERS](https://github.com/OpenEnvision/WorldFoundry/blob/main/.github/CODEOWNERS)
for review responsibility and retain contributor DCO trailers in squash commits.
These review conventions do not configure GitHub branch protection.

## Agent Skills

Repository [Agent Skills](https://github.com/OpenEnvision/WorldFoundry/blob/main/skills/index.md)
provide model integration, benchmark integration, inference optimization,
numerical validation, and repository maintenance workflows. Each directory uses
`SKILL.md` frontmatter with a name, description, license and environment needs;
references link to the owning architecture and validation contracts.
`CONTRIBUTING.md` and `AGENTS.md` remain authoritative.

Load a skill explicitly, or opt in through your client's local skill directory.
From the repository root, choose the command for your client:

```bash
# Clients that discover .agents/skills
mkdir -p .agents && ln -s ../skills .agents/skills
# Claude Code
mkdir -p .claude && ln -s ../skills .claude/skills
# Cursor
mkdir -p .cursor && ln -s ../skills .cursor/skills
```

These client directories are gitignored. For an existing skills directory, link
one selected skill instead:

```bash
mkdir -p .agents/skills
ln -s ../../skills/worldfoundry-model-integration .agents/skills/worldfoundry-model-integration
```

Validate metadata and repository links with
`python -m pytest -q tests/core/test_agent_skills.py`. The official
[skills-ref validator](https://github.com/agentskills/agentskills/tree/main/skills-ref)
checks the standard format with `skills-ref validate skills/<skill-name>`.
Format and link checks are separate from client activation and task quality:
evaluate representative tasks and a nearby non-triggering request in clean
contexts with and without the skill. Keep evaluation artifacts outside Git.

## Before a PR

Before opening a PR, confirm the following:

- **Scope** — Keep the change to one pipeline, benchmark path, runner layer, or documentation area.
- **Runtime** — Name the intended environment: runtime profile, hosted API, checkpoint-backed local run, plus any official repo provenance.
- **Assets** — Do not commit checkpoints, generated videos, local caches, credentials, or large downloaded datasets. Keep generated assets and benchmark data explicit, reproducible, and outside git.
- **Evidence** — Include commands, output paths, skipped stages, and blockers in the PR description.

## Code expectations

- **Python** — Keep imports lazy when a model or benchmark has heavy optional dependencies.
- **Public entry points** — Put user-facing runtime classes under `worldfoundry/pipelines/` or evaluation runners under `worldfoundry/evaluation/`.
- **Model runtimes** — Implement runtime integrations under `worldfoundry/synthesis/**` in-tree. Do not depend on machine-local external checkouts; record external repos/checkpoints only as provenance or acquisition metadata until ported or vendor-reviewed.
- **Vendored code** — Treat reviewed `thirdparty/` code as isolated code. Record its license name and upstream URL in the repository notice and provenance files linked from [Third-party notices](/docs/reference/vendored-licenses). Retain copyright notices and component license files required by the upstream terms; central provenance does not replace those obligations. Operational documentation belongs in Fumadocs rather than colocated README files. Prefer git submodules for large independently versioned upstreams; keep in-tree copies only when heavy patching is required. Do not duplicate code that already lives under `worldfoundry/base_models/` or `worldfoundry/synthesis/`. Current trees: FlashAttention is an external install (`scripts/setup/install_flash_attn.sh`); `diff-gaussian-rasterization/` is the canonical depth-capable Gaussian rasterizer; `simple-knn/` is the CUDA KNN extension; `fastvideo-kernel/` is the optional STA / VSA / VMoBA / TurboDiffusion kernel tree (build with `CUDA_HOME` + `./build.sh`; ThunderKittens only on Hopper `sm_90a` non-aarch64; FP4 attention only on Blackwell `sm_120a` with CUDA ≥ 12.8).
- **Synthesis** — Keep `worldfoundry/synthesis/**` infer-only: runtime wrappers, model code needed at inference time, checkpoint/path helpers, and minimal runtime configs. Do not add training launchers, dataset builders, demo media, notebooks, or generated outputs. Keep local demo assets under the gitignored `testcase/` directory.
- **Formatting** — Avoid large unrelated formatting changes. Do not rewrite generated or vendored files unless the task requires it.
- **Naming** — Prefer canonical ids and direct runner paths; when a public name changes, document the migration instead of adding long-lived compatibility maps.

## Validation selection

Match validation evidence to the surface you changed:

- **Runner, scorecard, tasks, registry** — Public CLI discovery, planning, and artifact validation commands.
- **Single pipeline run** — The smallest documented validation script and its generated manifest.
- **Stateful or interactive pipeline** — A documented stream command with bounded runtime evidence.
- **Benchmark runner** — Runner execution plus `zoo benchmark-run --mode official-validation` with official-shaped result files when normalizer review is needed.
- **Model runner** — Resolver/manifest validation plus a clear skipped path for missing checkpoint or credentials.

## Docs expectations

Fumadocs is the only maintained documentation surface. Add or update paired English and Chinese pages under `docs/fumadocs/content/docs`. The only `README.md` allowed in this repository is the root file. Do not add `README.md`, `readme.md`, or `README_*` next to source, vendor trees, fixtures, or model networks.

When you change behavior, update the page that owns it:

- **New model or runtime profile** — `guides/supported-models`, the per-model article at `guides/supported-models/<model-id>.mdx` (and `.zh.mdx`), `reference/environments`, and the model guide if behavior changes. Refresh checked-in homepage recipes and generated model pages with `npm --prefix docs/fumadocs run models:generate`, then verify them with `npm --prefix docs/fumadocs run models:check`. Set `pageSource: authored` on a model MDX file before hand-editing so later generates will not overwrite it. To refresh paper titles and teaser figures, run `npm --prefix docs/fumadocs run models:media` after generate.
- **New benchmark** — `evaluation/benchmark-hub/<benchmark-id>`, the benchmark guide, and maintainer architecture pages when internals change.
- **CLI or output schema** — `reference/cli` and architecture pages that own the changed behavior.
- **Internal workflow** — `maintainers/architecture` (especially workflow and evaluation-core).

Python-backed docs codegen and drift checks (`api:*`, `models:*`, `coverage:*`, and
`cli:screenshots`) go through `docs/fumadocs/scripts/run-python.sh`. Override the interpreter
with `WF_DOCS_PYTHON` (then `PYTHON`, then `python3` / `python`) when needed.

`npm run types:check` completes MDX generation before generating Next.js route
types, then runs TypeScript. The route-type command sets `_FUMADOCS_MDX=1`
to reuse the completed output rather than starting another background MDX
generation over the same files.

## Fast site iteration

Model demo videos are served from GitHub CDN; docs development does not need `git lfs pull`.

```bash
GIT_LFS_SKIP_SMUDGE=1 git clone https://github.com/OpenEnvision/WorldFoundry.git
```

WorldFoundry currently ships **one** maintained web site: the Fumadocs docs app at `docs/fumadocs/`. Homepage, benchmark hub, model catalog, and API reference are routes inside that app — not separate build targets. Studio (`worldfoundry/studio/`) is a Python FastAPI app, not a Next.js site.

Every site must keep **fast iteration** npm scripts in-repo. Production CI is unchanged (`scripts/docs/build.sh` → `deploy-docs.yml`).

From the repo root you can also use `make docs-dev-fast`, `make docs-dev-ssd`, `make docs-dev-local`, or `make docs-build-fast`.

The docs app contains hundreds of bilingual model and benchmark pages and large generated JSON catalogs. On a shared filesystem, `npm run dev` can feel slow because each start may rerun MDX codegen and cold webpack caches.

**Fastest dev on shared storage (recommended):**

```bash
cd docs/fumadocs
npm run dev:ssd
# or from repo root: make docs-dev-ssd
```

`dev:ssd` symlinks hot paths to local SSD (`~/.cache/worldfoundry-docs/<checkout-id>` by default): `tmp/` (Next.js + webpack), `.source/` (MDX codegen), and `node_modules/.cache`. Sources stay on the shared checkout — no full rsync on each start. First run migrates existing `.source/` output; Next.js and webpack caches are rebuilt on SSD.

For day-to-day UI/CSS polish when already on fast local disk:

```bash
cd docs/fumadocs
npm run dev:fast
```

`dev:fast` reuses existing `.source/` output without checking for content changes and reuses `generated/python-api.json` unless missing. Regenerate MDX after adding pages or changing navigation or frontmatter. Development caches use `tmp/` by default; on shared storage, prefer `dev:ssd` to place them on local SSD.

If `node_modules` I/O is also slow, mirror the whole site to local SSD:

```bash
cd docs/fumadocs
npm run dev:local
```

`dev:local` refreshes source files in a checkout-specific mirror under `/tmp/wf-docs-dev/<checkout-id>/WorldFoundry` and reuses its installed dependencies. Set `WF_DOCS_LOCAL_ROOT` to choose another mirror root.

To smoke-test static export locally without CI drift checks:

```bash
cd docs/fumadocs
npm run build:fast
```

SSD cache helpers: `npm run ssd:setup`, `npm run ssd:status`, `npm run ssd:clean` (add `-- --purge` to delete SSD data).

After changing model manifests, run `npm run models:generate` once, then `WF_DOCS_REFRESH_MDX=1 npm run dev` (or `npm run mdx:generate` while the dev server is stopped). Editing an existing MDX page during dev hot-reloads without regenerating `.source/`; new pages or `meta.json` changes require `WF_DOCS_REFRESH_MDX=1`.

`npm run dev:turbo` tries Turbopack instead of webpack. Treat it as experimental — production GitHub Pages still uses `npm run build` (webpack + static export).

### Adding a new site

When you add another Next.js or static site under `docs/<name>/`:

1. Add `dev:fast`, `dev:local` (optional SSD mirror script), and `build:fast` npm scripts.
2. Use env vars prefixed `WF_<SITE>_` (e.g. `WF_STUDIO_SKIP_MDX=1`) for skip/refresh toggles.
3. Add a `predev.mjs` (or equivalent) that smart-skips codegen when outputs are current.
4. Wire `make docs-<site>-dev-fast` targets if the site is commonly used from the repo root.
5. Extend the site catalog in this section (English and Chinese pages).

Production deploy speed is separate: CI runs full `types:check`, catalog drift checks, and static export for all pages. That path is unchanged.

## Local validation

```bash
bash scripts/setup/conda_install.sh --preset slim --env-name worldfoundry
make lint
make docs-check
cd docs/fumadocs && npm run types:check && npm run build
```

Public CPU checks do not require model weights:

```bash
python -m pip install -e ".[dev,test]"
make test-infer
make cli-check cli-entrypoint-check packaging-check
```

For model/profile audits:

```bash
worldfoundry-eval run --all-benchmarks --plan-only \
  --output-dir tmp/worldfoundry_plan_matrix \
  --json
worldfoundry-eval validate-artifact tmp/worldfoundry_plan_matrix/suite_manifest.json \
  --kind suite-manifest \
  --strict \
  --json
```

For staged zoo validation:

```bash
conda run -p "${WORLDFOUNDRY_UNIFIED_ENV_PREFIX}" worldfoundry-eval zoo models --json
conda run -p "${WORLDFOUNDRY_UNIFIED_ENV_PREFIX}" worldfoundry-eval zoo benchmarks --json
conda run -p "${WORLDFOUNDRY_UNIFIED_ENV_PREFIX}" worldfoundry-eval run --all-benchmarks --plan-only --output-dir tmp/worldfoundry_plan_matrix --json
conda run -p "${WORLDFOUNDRY_UNIFIED_ENV_PREFIX}" worldfoundry-eval validate-artifact tmp/worldfoundry_plan_matrix/suite_manifest.json --kind suite-manifest --strict --json
```

## PR evidence template

```md
## Scope
- Changed:
- Not changed:

## Evidence
- Command:
- Output:
- Scorecard/report:
- Skipped stages:
- Blockers:

## Docs
- English page:
- Chinese page:
```

<Callout title="Review rule">
  A PR can add planned or source-verified entries without runnable support. It must not claim demo parity, checkpoint parity, or benchmark readiness without matching fresh evidence.
</Callout>


Public test sources live under `tests/`; model weights, test media and generated replay evidence stay outside git. Inference changes must replay affected real-checkpoint cases and pass `make test-geometry` against an accepted reference. See [Validation](/docs/reference/validation) for numerical comparison and source-hash verification.
