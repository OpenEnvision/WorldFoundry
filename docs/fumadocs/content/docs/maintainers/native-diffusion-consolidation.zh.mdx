native-diffusion 各 family 的**整合状态**：每个模型复用了哪些 canonical role、支撑各 recipe 的本地结构/checkpoint 验证，以及尚未完成的 CUDA artifact parity。采样内核、组件边界、依赖规则与迁移*过程*见 [原生扩散](/zh/docs/maintainers/architecture/native-diffusion)；这些 family 依赖的共享原语见 [核心基础设施](/zh/docs/maintainers/architecture/core-infrastructure)。

<Callout type="info">
  下文反复出现一个区分：**结构/checkpoint 验证**（与已发布 checkpoint 的逐 key/tensor 精确覆盖）不等于 **CUDA artifact parity**（真实 GPU 运行产出一致输出）。CUDA parity 按 family 是独立 release gate，不能由结构验证替代。
</Callout>

## Scheduler 与组件整合

Wan shifted trajectory 是 canonical 实现，flow UniPC/DPM++ 只在 `schedulers/` 下保留一份实现。Wan 与 Cosmos compatibility path 都解析到同一个 native UniPC class；Wan 的六个 DPM++ 和六个 UniPC 入口是单向 export。验证覆盖 schedule construction、noise interpolation、flow conversion 与完整 multistep trajectory。FLUX.2 的 latent autoencoder 位于 `models/autoencoders/flux2`，加载复用 core-backed module loader，benchmark caller 使用 canonical path。

## Sana

Sana image、video、streaming、ControlNet 与 SANA-WM variant 和其他 diffusion family 共用同一套 role-based package。Checkpoint-shaped network math 位于 `models/networks/sana`，DC-AE 位于 `models/autoencoders/sana`，conditioning 位于 `models/encoders/sana`，构造逻辑属于 recipe 与 scheduler。其 Wan VAE variant 使用框架无关 adapter，不继承 Diffusers mixin。Shape、volume、configuration filtering、state-dict prefix 与 Triton autotune helper 来自 `worldfoundry/core`。

## Wan family

`wan2.1-t2v-1.3b` 是参考内置 native recipe。UMT5 conditioner、tokenizer resource、DiT、latent initializer、shifted Euler scheduler 和 VAE decoder 全部由 standard strategy 装配。Checkpoint resolver 会先请求 `worldfoundry/core` 解析本地 staged Hub snapshot，找不到时才执行 filtered Hub materialization；revision 与 required files 始终保持 declarative。本地 checkpoint 结构验证确认 DiT（825）、text encoder（242）和 VAE（194）全部逐键匹配。该 recipe 的 CUDA artifact parity 仍是独立 release gate。

所有 Wan 衍生产品也复用同一组 role，不携带私有 Wan framework。PUSA、SAMA、Spatia、MultiWorld、FantasyWorld 与 WoW 组合 canonical Wan transformer、conditioning、codec、checkpoint loading、LoRA/control helper 和 staged runner，只保留 checkpoint-visible 的差异。本地精确图检查覆盖 MultiWorld（984/984 tensors）、FantasyWorld 的 Wan2.1 overlay（3,132/3,132）和 Wan2.2 high/low 两个分支（分别为 2,658/2,658），以及 WoW 1.3B（825/825）。WoW 的网络图直接由发布的 transformer checkpoint 推导，并正确选择仅 VAE 的首帧 conditioning。WoW DiT 2B 把 post-trained transformer checkpoint 交给 canonical Cosmos Predict2 route，不自带 scheduler、tokenizer 或 pipeline。由于 pinned Hub snapshot 中不存在预期的 `wow_dit_2b.pt`，其 checkpoint graph 与 CUDA artifact parity 仍待验证。这些 Wan 衍生产品的 CUDA artifact parity 仍未完成。

## Matrix Game 3.5

`matrix-game-3.5-first-person` 与 `matrix-game-3.5-third-person` 是默认 registry 中两个独立冻结的 recipe，分别直接绑定发布的完整 829-key DiT checkpoint。逐 key/shape 的 header-to-model 验证固定了第一人称 checkpoint 的 subject-reference embedding 容量为 2、第三人称为 4；产品 profile 仍把单次第三人称请求限制为最多两个 reference。它们复用 canonical Wan UMT5 conditioner、48-channel Wan2.2 VAE、latent initializer、scheduler、core attention、loader 与 standard runner；结构验证同时逐一匹配 242 个 text-encoder key 与 converter 处理后的 196 个 Wan2.2 VAE key。Mosaic、PRoPE 和 subject-memory tensor computation 位于 Matrix denoiser component；synthesis route 把 `DiffusionRequest` 直接交给 `NativeDiffusionPipeline`。Runtime config 只暴露 inference 语义。native recipe 的 CUDA artifact parity 仍未完成。

## Echo Memory

Echo Memory 在同一个默认 registry 中注册 11 个不可变 model recipe。每个公开 model ID 都固定自己的 checkpoint file 与 memory architecture，不作为共享可变 Echo pipeline 的 option。Denoiser 在 canonical Wan blocks 上安装 checkpoint-compatible Echo module；conditioner、VAE、core loading、UniPC scheduler、runner 与 runtime policy 均复用共享 infra。框架自有的 `frozen-context` strategy 负责将 target noise 与 clean context suffix 组合、每个 solver step 后重新锁定 context，并只 decode target latent。已发布 K=1 checkpoint 的 1,185 个 tensor 均与 native model 精确覆盖。native CUDA artifact parity 仍未完成。

## LTX

`ltx-2-i2v`、`ltx-2.3-i2v` 与 `ltx-video-i2v` 是三个独立 recipe，但共用同一个 `NativeDiffusionPipeline`、复用 core 的 loader、runtime policy 和框架自有 `joint-multistage` runner。LTX-2.x 在低分辨率生成与空间 refinement 两个阶段联合处理视频和音频；LTX-Video 0.9.8 则以单视频模态在同一 runner 中执行两个阶段，并在阶段之间应用 spatial upsampler。Transformers 只提供 checkpoint-compatible Gemma/T5 architecture，不作为 inference backend。真实本地 checkpoint 已逐角色精确覆盖：LTX-2 transformer 3,510、connector 59、video encoder/decoder 94/92、audio decoder 58、vocoder 194、upsampler 73、statistics 2、Gemma 1,066；LTX-2.3 transformer 4,186、connector 262、video encoder/decoder 86/86、audio decoder 58、vocoder 1,227、upsampler 72、statistics 2、Gemma 1,066；LTX-Video transformer 1,215、video encoder/decoder 94/134、T5 220。CUDA artifact parity 仍是独立 release gate。

`ltx-2.5` 在同一边界上使用拆分 checkpoint recipe。规范 LTX 组件负责 Gemma 4 及其投影/connector、Transformer、DiffVAE、音频 VAE/BWE vocoder、空间上采样器和可选时长预测头；共享 core 组件负责惰性加载、量化、卸载与 SDR H.264/AAC 编码；`synthesis` 和 `pipelines` 只保留请求与产物适配。缩小的随机拆分 checkpoint 在 CPU 上精确复现固定上游版本（`a95ab856`）的各阶段 latent、解码帧与音频，覆盖 T2V、首帧/后续帧 I2V、自动时长、生成关键帧与重复请求，包括磁盘卸载加载路径。发布权重 header/meta 的 key 与 shape 映射覆盖全部十组组件；合成 SDR 编码 fixture 的输出字节也完全一致。这些 CPU fixture 不代表发布权重质量；GPU/MPS、量化内核、异步卸载与发布权重产物一致性仍是 release gate。

## Cosmos Predict 2.5 / Transfer 2.5

Cosmos Predict 2.5 与 Transfer 2.5 遵循同一规则。Predict 2B、Predict 14B 和 Transfer 2B controlled-video 三个 recipe 共用一套 native runner、Reason1 conditioner、Wan codec 实例、Karras flow-UniPC scheduler、core loader 与 offload policy。Transfer 只增加 checkpoint-shaped VACE 网络分支——位于 base DiT 第 0/7/14/21 层的 4 个 control block，以及支持 8 modality 的 control embedder——不增加 ControlNet backend 或 family runner。已发布的 Predict 与 Transfer 配置都关闭 temporal FPS RoPE modulation。本地精确结构验证覆盖 Predict 2B（569 个 transformer tensor）、Predict 14B（729）、Reason1 language weights（338）与 Wan codec（194）；native Transfer control path 也通过有限值 tiny forward。由于本机没有精确 general/edge asset，Transfer checkpoint 结构与完整 native CUDA artifact parity 仍待验证。

## Cosmos Predict1 / Predict2 (GEN3C)

Cosmos Predict1 与 Predict2 复用上述架构。`gen3c-cosmos1-7b` 绑定 570-tensor 原生 DiT、共享 T5-11B conditioner、Cosmos Tokenize1 codec、Karras x0 AB2 与标准 initializer；MoGe depth、命名 camera path 和 RGBD forward warp 是复用 `worldfoundry/core` geometry 的模型预处理，不是 GEN3C runner。`cosmos-predict2-2b-video2world` 与 `cosmos-predict2-14b-video2world` 共用 Predict2/2.5 backbone module 和 Wan codec，recipe 配置只选择 567/727-tensor topology、T5-11B、sigma-max initialization 与 Rectified Flow AB2。两代模型都通过框架提供的 terminal clean-prediction lifecycle 完成末次去噪，不持有 family runner。Registry、tiny-forward、mask、geometry 与 scheduler validation 已在本地通过；Predict2 权重受 gated access 限制，两代模型的完整 native GPU artifact parity 仍待完成。

## HunyuanVideo

HunyuanVideo 同样遵守这一组合边界。`hunyuanvideo-t2v`、`hunyuanvideo-i2v`、`hunyuanvideo-1.5-t2v` 与 `hunyuanvideo-1.5-i2v` 是默认 registry 中四个不可变 recipe，全部使用 standard framework runner。原版与 1.5 只拥有 checkpoint-compatible denoiser、prompt conditioning 和 latent codec；scheduler、loader、offload、execution、media IO 与公开 pipeline 行为继续复用共享 infra。MLP、text/timestep projection、AdaLN/final layer、prefix modulation、attention 与 RoPE helper 统一解析到共享 core primitive，同时保持 checkpoint 可见的 submodule name 不变。本地精确 checkpoint 检查覆盖转换后的原版 T2V DiT（856 个源 key 转为 976 个原生 key）、原版 I2V DiT（856 keys）、原版 causal VAE（248 keys）、1.5 DiT（1,793 keys）、1.5 VAE（218 keys）与仅 I2V 使用的 SigLIP vision encoder（448 keys），missing、unexpected 与 shape mismatch 全部为 0。受限访问的 FLUX.1-Redux-dev vision asset 是显式 I2V component dependency，不通过 sibling directory 猜测。原版 causal 3D VAE 是 encode/decode 共用的单一原生 PyTorch module。四个 recipe 都仍需完成 checkpoint-backed CUDA artifact parity。Hunyuan GameCraft 保留自己的 synthesis 层采样循环，而不是使用这些 native recipe。

## Self-Forcing 与 Causal-Forcing

`self-forcing` 与四个 Causal-Forcing 学生（公开 ID `causal-forcing` 解析到的 `causal-forcing-chunkwise`，以及 `causal-forcing-framewise`、`causal-forcing-framewise-1step`、`causal-forcing-framewise-2step`）是运行在框架自有 `autoregressive-window` runner 上的不可变 recipe。它们共用一个 recipe 构造函数：带 21 个 latent 帧 KV cache、做蒸馏 x0 预测的因果 Wan2.1 1.3B denoiser，canonical Wan2.1 umT5 conditioner，shift 5 时间表上的 Wan flow-match scheduler，以及 bf16 的 Wan2.1 codec。各发布版本只在 generator 文件、latent 块大小、固定步数表（Causal Forcing++ 首块为四步）以及是否用图像作为首个 latent 帧上不同。`NativeSelfForcingPipeline` 与 `NativeCausalForcingPipeline` 是 catalog binding 与 Studio 共用的公开 pipeline，并提供同一套常驻实时会话。

只有 RollingForcing 使用 `synthesis/visual_generation/forcing/runtime.py` 中的子进程桥接，以已安装的 `worldfoundry.synthesis.visual_generation.rolling_forcing.inference` 模块启动。它保留 `forcing/shared/` 和 `forcing/causal_forcing_runtime/long_video/` 中的滚动窗口 pipeline。Self-Forcing 与 Causal-Forcing 通过原生 pipeline 运行，不再包含子进程桥接分支。每个发布版本的已验收参考一致性均为逐位一致：严格 checkpoint 加载、提示词嵌入、每次 generator 调用、rollout 最终 latent 以及参考 latent 的解码都与官方推理脚本的录制运行一致（`tests/manual/self_forcing_parity.py`），回放案例 `self-forcing-t2v-short`、`causal-forcing-chunkwise-t2v-short` 与 `causal-forcing-framewise-short` 覆盖公开路线。

## LVDM

LVDM 的 checkpoint-shaped 实现按 role 拆分：

- `models/networks/lvdm`：latent-diffusion 编排、3D UNet 与 checkpoint-visible attention block；
- `models/autoencoders/lvdm`：latent codec；
- `models/encoders/lvdm`：text、image、adapter 与 resampler conditioning；
- `schedulers/lvdm`：DDIM variant、diffusion schedule 与 Vid2World KV cache；
- `core/configuration/factory.py` 与 `core/nn`：通用 config 构造、distributions、EMA、checkpoint 与经典卷积 helper。

Vid2World dataset adapter 属于其 synthesis 包 `synthesis/visual_generation/vid2world/eval_inputs`。Runtime config 必须使用这些 role-based 全限定路径。

### LVDM fork 状态

- **T2V-Turbo** — 共享 role-based component。其 VideoCrafter2 base 解析公共 network、codec、encoder 与 scheduler role，只保留自己的 LoRA 与 consistency-sampling 行为。
- **VideoCrafter** — 共享 role-based component。所有打包 config 直接指向 canonical role package，不再复制 framework tree。
- **Dynamicrafter、MotionCtrl** — 共享 role-based component。现有 synthesis adapter 保留各自产品行为，同时 import 同一组 LVDM component。
- **Vid2World** — 共享 component + 显式扩展。其改造的 latent diffusion network、UNet、attention、DDIM sampler 与 KV cache 作为命名 role component；dataset 仍归 synthesis。

### Guard rails

对每个 LVDM 衍生集成：

1. checkpoint-visible 结构一致时必须复用 canonical role component。
2. 仅当 checkpoint 或 inference 行为不同时，才新增一个窄命名的 role component。
3. 编排放在 native recipe/pipeline，data adapter 放在 synthesis。
4. 在有资产时执行 `compileall`、target 解析、checkpoint key/shape 检查，并跑相关 integration test 子集。

不要再引入 model-local 的 `models/modules/pipeline/scheduler` framework 层级。
