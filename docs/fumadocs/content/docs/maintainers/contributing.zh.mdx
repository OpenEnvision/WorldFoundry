## 仓库协作流程

根目录 [CONTRIBUTING.md](https://github.com/OpenEnvision/WorldFoundry/blob/main/CONTRIBUTING.md)
统一定义代码和 PR 规范。开发、推理、Studio 与评测使用同一个 GPU 环境。
每个贡献 commit 都需要 [Developer Certificate of Origin](https://developercertificate.org/)
签名确认，即 `git commit --signoff`。Commit subject 和 PR 标题统一使用 `[type]Description`，
右括号后不加空格，描述使用英文祈使句，例如 `[test]Cover session cleanup`。

参与者遵守[行为准则](https://github.com/OpenEnvision/WorldFoundry/blob/main/CODE_OF_CONDUCT.md)。
潜在漏洞通过[安全政策](https://github.com/OpenEnvision/WorldFoundry/blob/main/SECURITY.md)中的私密渠道报告。
一方贡献采用 [Apache License 2.0](https://github.com/OpenEnvision/WorldFoundry/blob/main/LICENSE)，
保留的上游许可条款记录在[第三方许可与来源](/zh/docs/reference/vendored-licenses)。

新增 Python 函数和公开契约必须有类型注解。Ruff 统一格式和 import 顺序，ty 检查类型。
pre-commit 检查 staged 文件，PR 的 `Python quality` 检查变更 Python 文件。
保留上游署名及导入代码的检查排除规则。无权重的单元测试标记为 `unit`，CUDA 测试标记为
`gpu`，手动推理脚本放在 `tests/manual/` 或 `tests/stream/`。

CODEOWNERS 覆盖整个仓库。PR 需要适用的 CI 结果和维护者/code owner 的批准。
使用 squash merge 和描述性 PR 标题，并保留 DCO trailers。管理员按 CONTRIBUTING.md
配置 `main` 的 ruleset。

## Agent Skills

仓库维护的 [Agent Skills](https://agentskills.io/specification) 放在
[`skills/`](https://github.com/OpenEnvision/WorldFoundry/tree/main/skills)。
[技能索引](https://github.com/OpenEnvision/WorldFoundry/blob/main/skills/index.md)
覆盖模型集成、benchmark 集成、推理优化、推理验证和仓库维护。
每项技能使用 `SKILL.md`，包含 YAML `name`、`description` 和链接到当前框架契约的 Markdown 指令。

工作流包括先做组件级数值对齐、校验 checkpoint 转换、定位首个数值偏差、确认实际执行后端，
以及分别测量冷启动和稳态性能。Compile、CUDA graph、warmup 与 offload 任务按需加载执行生命周期参考，
数值比较失败时加载 parity 参考。技能索引记录借鉴的上游工作流来源。
所有命令和门禁仍由 WorldFoundry 的架构与验证契约统一定义；模型集成不代表服务可靠性已验证。

可以显式加载对应的 `SKILL.md`，也可以按需接入客户端的本地技能目录。
从仓库根目录运行对应客户端的命令：

```bash
# 发现 .agents/skills 的客户端
mkdir -p .agents && ln -s ../skills .agents/skills

# Claude Code
mkdir -p .claude && ln -s ../skills .claude/skills

# Cursor
mkdir -p .cursor && ln -s ../skills .cursor/skills
```

这些客户端目录已被 Git 忽略。若只需向已有技能目录加载一项技能，可以单独链接：

```bash
mkdir -p .agents/skills
ln -s ../../skills/worldfoundry-model-integration .agents/skills/worldfoundry-model-integration
```

发现与启用方式取决于客户端配置。Skills 补充 `AGENTS.md` 和 CONTRIBUTING.md，
仓库规则仍由这两份文件统一维护。目录索引使用 `skills/index.md`，
仓库仍只保留根目录的一份 README。

### 编写与验证

遵循官方[格式规范](https://agentskills.io/specification)和
[编写最佳实践](https://agentskills.io/skill-creation/best-practices)。

- `SKILL.md` 以 YAML frontmatter 开始。必需字段为 `name` 和 `description`，正文描述任务步骤。
- 名称为 1–64 个小写字母、数字或连字符，不能有首尾或连续连字符，且必须与父目录名称一致。
  仓库技能使用 `worldfoundry-` 前缀。
- 描述非空且不超过 1024 字符，以 “Use this skill when…” 开头，说明用户意图及适用任务场景。
- `license`、`compatibility`、`metadata` 和 `allowed-tools` 是标准中的可选字段。
  仓库技能声明 `Apache-2.0`；有特定 checkout 或环境要求时使用 `compatibility`，最多 500 字符。
- 每项技能保持聚焦，`SKILL.md` 少于 500 行。发现阶段只加载名称和描述，启用阶段加载指令，
  执行阶段按需读取参考文件。说明何时加载参考内容，文件链接相对于技能目录解析，
  仓库命令从仓库根目录执行。
- 按任务需要添加 `scripts/`、`references/` 或 `assets/`。脚本使用显式参数、声明依赖、提供
  `--help` 且非交互执行；新增随技能分发的资源需纳入 `MANIFEST.in`。

安装官方 [skills-ref 参考 CLI](https://github.com/agentskills/agentskills/tree/main/skills-ref) 后，
从仓库根目录验证格式和仓库引用：

```bash
skills-ref validate skills/worldfoundry-model-integration
python -m pytest -q tests/core/test_agent_skills.py
```

格式通过不代表触发可靠性或任务效果已验证。
[行为评测](https://agentskills.io/skill-creation/evaluating-skills)先选两三项代表性任务，
再增加一个相近但不应触发技能的请求。分别在加载与不加载技能的干净上下文中执行，
检查是否读取了对应 `SKILL.md`，并比较实际输出和命令。
生成的评测产物放在 `tmp/`，不进入 Git。

## PR 前检查

提交 PR 前，请确认：

- **范围** — 一次只改一个 pipeline、benchmark path、runner layer 或文档区域。
- **Runtime** — 写清目标环境：runtime profile、hosted API、checkpoint-backed local run，以及任何 official repo provenance。
- **资产** — 不提交 checkpoint、生成视频、本地 cache、凭据或大型下载数据集。生成资产和 benchmark 数据要明确、可复现，并放在 git 之外。
- **证据** — PR 描述中包含命令、输出路径、跳过阶段和 blocker。

## 代码要求

- **Python** — 模型或 benchmark 有重依赖时保持 lazy import。
- **公开入口** — 用户可见 runtime class 放在 `worldfoundry/pipelines/`；评测适配器放在 `worldfoundry/evaluation/`。
- **Model runtimes** — `worldfoundry/synthesis/**` 下的 runtime integration 必须仓内实现。不要依赖机器本地的外部 checkout；外部仓库/checkpoint 在移植或 vendor review 前只能记录为 provenance 或 acquisition metadata。
- **Vendored code** — 已 review 的 `thirdparty/` 代码按隔离代码处理。许可名称和上游 URL 记录在[第三方许可与来源](/zh/docs/reference/vendored-licenses)所链接的仓库声明与来源文件中，保留上游分发条款要求的组件许可文件，并在 package data 中声明；许可门禁记录已审查的例外。项目许可证放在根目录，来源记录保存在集中声明中，操作文档维护在 Fumadocs。大型、独立版本的上游优先用 git submodule；只有需要重度打补丁时才仓内拷贝。不要再复制已经在 `worldfoundry/base_models/` 或 `worldfoundry/synthesis/` 里的代码。当前树：FlashAttention 是外部安装（`scripts/setup/install_flash_attn.sh`）；`diff-gaussian-rasterization/` 是带深度的规范高斯光栅器；`simple-knn/` 是 CUDA KNN 扩展；`fastvideo-kernel/` 是可选的 STA / VSA / VMoBA / TurboDiffusion kernel 树（`CUDA_HOME` + `./build.sh`；ThunderKittens 只在非 aarch64 的 Hopper `sm_90a`；FP4 attention 只在 Blackwell `sm_120a` 且 CUDA ≥ 12.8）。
- **Synthesis** — 保持 `worldfoundry/synthesis/**` 仅用于推理：runtime wrapper、推理所需模型代码、checkpoint/path helper 和最小 runtime config。不要添加 training launcher、dataset builder、demo 媒体、notebook 或生成输出。本地 demo 资产放在已被 Git 忽略的 `testcase/` 目录。
- **Formatting** — 避免无关大规模格式化；除非任务需要，不重写生成文件或 vendored 文件。
- **Naming** — 优先使用 canonical id 和直接 runner path；公开名称变化时，写 migration 说明，而不是长期保留 compatibility map。

## 验证方式

按变更类型选择验证证据：

- **Runner、scorecard、tasks、registry** — 使用公开 CLI 的 discovery、plan 和 artifact validation 命令。
- **单 pipeline run** — 使用最小的文档化验证脚本及其生成 manifest。
- **Stateful / interactive pipeline** — 使用文档化 stream 命令，并提供有界 runtime 证据。
- **Benchmark runner** — Runner execution；需要 normalizer review 时，用 official-shaped result files 跑 `zoo benchmark-run --mode official-validation`。
- **Model runner** — Resolver/manifest validation，并为缺 checkpoint/credentials 提供 skipped path。

## 文档要求

Fumadocs 是唯一维护的文档面。新增或修改页面时，在 `docs/fumadocs/content/docs` 下维护英文和中文成对页面。本仓库只允许根目录那一份 `README.md`。不要在源码、vendor 树、fixture 或模型网络旁再加 `README.md`、`readme.md` 或 `README_*`。

行为变更时，更新对应 owning page：

- **新模型或 runtime profile** — `guides/supported-models`、对应的 `guides/supported-models/<model-id>.mdx`（及 `.zh.mdx`）、`reference/environments`，行为变化时更新模型指南。先用 `npm --prefix docs/fumadocs run models:generate` 刷新已检入的 homepage recipes 和生成的模型页，再用 `npm --prefix docs/fumadocs run models:check` 验证。手写模型文请先把 frontmatter 的 `pageSource` 设为 `authored`，以免再次 generate 时被覆盖。论文标题与配图用 `npm --prefix docs/fumadocs run models:media` 在 generate 之后刷新。
- **新 benchmark** — `evaluation/benchmark-hub/<benchmark-id>`、benchmark 指南；内部实现变化时同步维护者架构页。
- **CLI 或输出 schema** — `reference/cli`，以及拥有相关行为的 architecture 页面。
- **内部 workflow** — `maintainers/architecture`（尤其是 workflow 与 evaluation-core）。

基于 Python 的文档 codegen 与漂移检查（`api:*`、`models:*`、`coverage:*` 和
`cli:screenshots`）统一经 `docs/fumadocs/scripts/run-python.sh` 调用解释器。需要覆盖时，
解析顺序为 `WF_DOCS_PYTHON`、`PYTHON`、`python3`、`python`。

## 文档启动与发布

文档应用使用 Next.js 16、React 19、Fumadocs 和 Tailwind CSS 4。
准备 Node.js 22（见 `docs/fumadocs/.nvmrc`）、npm 和统一 Python 环境。
在仓库根目录执行：

```bash
npm --prefix docs/fumadocs ci
npm --prefix docs/fumadocs run dev
bash scripts/docs/build.sh
npm --prefix docs/fumadocs start
```

开发与静态预览地址均为 `http://localhost:3000`，包含 `/docs` 和 `/zh/docs`。
依赖已安装时可给构建命令添加 `--skip-install`。构建先检查类型与生成数据，
再导出至 `docs/fumadocs/out/`。

`docs/fumadocs/` 内，`app/` 管理路由，`components/` 管理共享 UI，
`content/docs/` 保存双语页面，`content/blog/` 保存文章，`mdx/partials/`
保存共享正文，`lib/` 保存工具与目录数据，`public/` 保存资源，`scripts/`
保存工具脚本。`source.config.ts` 配置集合，`next.config.mjs` 配置静态导出与缓存。
`.source/`、`generated/`、`tmp/`、`.next/` 和 `out/` 为生成目录。
输入变化后运行 `api:generate`、`models:generate`、`benchmarks:generate` 或
`coverage:generate`，再运行对应的 `*:check`。`models:homes:check` 检查模型页；
`types:check` 生成 MDX/类型并检查 TypeScript。

`.github/workflows/deploy-docs.yml` 在匹配的 `main` 变更或手动触发时发布静态站点。
部署构建前设置：

| 变量 | 官方部署值 |
| --- | --- |
| `NEXT_PUBLIC_BASE_PATH` | `/WorldFoundry`；本地开发留空。 |
| `NEXT_PUBLIC_SITE_URL` | `https://openenvision.github.io`。 |
| `NEXT_PUBLIC_DEMO_ASSET_BASE_URL` | `docs/fumadocs/public` 对应的 GitHub media CDN。 |

演示视频保留在 CDN，不放入 Pages 产物。

## 快速站点迭代

模型演示视频由 GitHub CDN 提供，文档开发不需要执行 `git lfs pull`。

```bash
GIT_LFS_SKIP_SMUDGE=1 git clone https://github.com/OpenEnvision/WorldFoundry.git
```

WorldFoundry 目前只维护 **一个** Web 站点：`docs/fumadocs/` 下的 Fumadocs 文档应用。Homepage、benchmark hub、模型目录和 API 参考都是该应用内的路由，不是独立构建目标。Studio（`worldfoundry/studio/`）是 Python FastAPI 应用，不属于 Next.js 站点。

每个站点都应在仓库内保留 **快速迭代** 的 npm 脚本。生产 CI 路径不变（`scripts/docs/build.sh` → `deploy-docs.yml`）。

在仓库根目录也可使用 `make docs-dev-fast`、`make docs-dev-ssd`、`make docs-dev-local` 或 `make docs-build-fast`。

文档站点包含数百个中英双语模型与 benchmark 页面，以及体积较大的生成 JSON 目录。在共享文件系统上，每次 `npm run dev` 都可能重跑 MDX codegen 并冷启动 webpack 缓存，体感较慢。

**共享存储上最快的 dev（推荐）：**

```bash
cd docs/fumadocs
npm run dev:ssd
# 或从仓库根目录：make docs-dev-ssd
```

`dev:ssd` 将热点路径符号链接到本地 SSD（默认 `~/.cache/worldfoundry-docs/<checkout-id>`）：`tmp/`（Next.js + webpack）、`.source/`（MDX codegen）、`node_modules/.cache`。源码仍留在共享 checkout，每次启动不做全量 rsync。首次运行会迁移已有 `.source/` 产物；Next.js 与 webpack 缓存会在 SSD 上重建。

日常 UI/CSS 打磨（已在本地快盘时）：

```bash
cd docs/fumadocs
npm run dev:fast
```

`dev:fast` 直接复用已有 `.source/`，不检查内容是否更新，并在 `generated/python-api.json` 存在时复用它。新增页面或修改导航、frontmatter 后需要重新生成 MDX。开发缓存默认放在 `tmp/`；共享存储上优先用 `dev:ssd` 将缓存放到本地 SSD。

若 `node_modules` 读写也慢，可将整个站点镜像到本地 SSD：

```bash
cd docs/fumadocs
npm run dev:local
```

`dev:local` 会刷新 `/tmp/wf-docs-dev/<checkout-id>/WorldFoundry` 下当前 checkout 专用镜像的源码，并复用已安装依赖。可通过 `WF_DOCS_LOCAL_ROOT` 指定其他镜像根目录。

本地快速验证静态导出（不跑 CI 漂移检查）：

```bash
cd docs/fumadocs
npm run build:fast
```

SSD 缓存辅助命令：`npm run ssd:setup`、`npm run ssd:status`、`npm run ssd:clean`（加 `-- --purge` 可删除 SSD 上的缓存数据）。

修改模型 manifest 后，先运行一次 `npm run models:generate`，再执行 `WF_DOCS_REFRESH_MDX=1 npm run dev`（或在停掉 dev server 后运行 `npm run mdx:generate`）。开发中编辑已有 MDX 页面可直接热更新，无需重新生成 `.source/`；新增页面或修改 `meta.json` 时需设置 `WF_DOCS_REFRESH_MDX=1`。

`npm run dev:turbo` 尝试使用 Turbopack 替代 webpack，目前视为实验性；生产 GitHub Pages 仍走 `npm run build`（webpack + 静态导出）。

### 新增站点

在 `docs/<name>/` 下新增 Next.js 或静态站点时：

1. 添加 `dev:fast`、`dev:local`（可选 SSD 镜像脚本）和 `build:fast` npm 脚本。
2. 跳过/刷新类环境变量使用 `WF_<SITE>_` 前缀（例如 `WF_STUDIO_SKIP_MDX=1`）。
3. 提供 `predev.mjs`（或等价逻辑），在输出已是最新时智能跳过 codegen。
4. 若需从仓库根目录常用，添加对应的 `make docs-<site>-dev-fast` 目标。
5. 在本节站点目录（中英文页面）中补充一条。

生产部署速度是另一回事：CI 仍会跑完整的 `types:check`、目录漂移检查和全页静态导出，该路径未改动。
